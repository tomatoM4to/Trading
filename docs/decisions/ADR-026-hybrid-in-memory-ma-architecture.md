# ADR-026: Hybrid In-Memory MA Architecture (Zero-Latency Screener)

## Status
Accepted (Supersedes ADR-016, ADR-025)

## Date
2026-08-08

## Context
ADR-025까지 우리는 스크리너 쿼리의 속도를 끌어올리기 위해 SQLite 엔진 내부에서 `AVG(...) OVER(...)` 등의 윈도우 함수를 조율하는 극한의 푸시다운(Push-down) 및 역방향 윈도우(Reverse Windowing) 최적화를 수행했습니다. 그러나 1GB RAM (Oracle Cloud) 환경에서 이 방식은 근본적인 한계에 봉착했습니다.
1. **반복 연산 오버헤드**: 스크리너에 클라이언트 요청이 들어올 때마다, 매번 수많은 종목의 윈도우(최대 200일) 데이터를 실시간으로 다시 스캔하고 더하는(`SUM`, `AVG`) 중복 연산이 발생했습니다. 
2. **복잡한 쿼리 의존성**: 정배열, 크로스, 수렴 등의 조건을 구현하기 위한 CTE 단계가 너무 길고 복잡해지며 쿼리 디버깅 및 유지보수가 기하급수적으로 어려워졌습니다.
3. **디스크 I/O 위험성**: 물리 디스크 DB에 담긴 방대한 과거 OHLCV를 수시로 풀스캔하는 행위는 결국 시스템 I/O 병목을 유발합니다.

Pandas 등의 외부 라이브러리는 DataFrame 객체 자체의 메모리 오버헤드가 너무 커서 도입이 불가능했습니다 (ADR-014). 이에 파이썬 내장 자료구조만을 이용해 극단적으로 메모리를 아끼는 완전히 새로운 MA 연산/저장 파이프라인이 필요해졌습니다.

## Decision
무거운 SQLite 윈도우 함수 방식을 전면 폐기하고, **"순수 파이썬 캐시 엔진 + 전용 휘발성 인메모리 DB"**의 이원화 구조(Hybrid Architecture)를 채택합니다.

### 1. Pure Python `MACalculator` 도입
- `collections.deque(maxlen=window)`를 이용해 각 종목별로 O(1) 시간 복잡도를 가지는 Rolling Average 연산 엔진을 구축했습니다.
- 백그라운드 스케줄러가 새 캔들을 수집할 때마다 종가(`close`) 하나만 이 캐시 객체에 밀어 넣고, O(1)로 갱신된 최신 이평선 값들(`ma5` ~ `ma200`)을 즉시 반환받습니다.

### 2. 데이터 분리 적재 (Persistent vs Volatile)
- **원본 OHLCV**: 기존과 동일하게 영구 보존용 물리 디스크 DB(`trading.db`)에 저장합니다.
- **연산된 MA**: 물리 디스크에 일절 저장하지 않으며, 오직 앱 구동과 함께 생성되는 휘발성 인메모리 DB(`file:ma_db?mode=memory&cache=shared`)의 `daily_ma`, `minute_ma` 테이블에만 저장(Insert)합니다. 

### 3. 실시간 MA 수화(Hydration) 파이프라인
- 앱 콜드 스타트 또는 매일 08:00 스케줄러 실행 시, 디스크에서 과거 OHLCV를 일괄로 꺼내어 `MACalculator`를 통과시킨 후 MA 인메모리 DB를 통째로 리빌드(Bulk Insert)합니다.
- 분봉은 메모리 최적화를 위해 전체 캔들이 아닌 **최근 3일 치** 캔들만 추출해 리빌드합니다. (1일=390봉이므로 3일=1,170봉이며, 200 이평선 예열을 위한 199봉을 충분히 커버함)

## Consequences
- **극단적인 속도 향상**: 스크리너 쿼리 내부의 윈도우 함수가 완전히 사라졌으며, 쿼리는 `SELECT * FROM minute_ma WHERE ticker IN (...)`와 같이 완성된 값을 단순히 읽어 들이는 구조로 다이어트되었습니다. 이는 스크리너 엔진의 레이턴시를 0초(Zero-latency)에 가깝게 만듭니다.
- **디스크 I/O 제로**: 클라이언트가 스크리너를 아무리 많이 호출해도 물리 디스크는 1 바이트도 읽히지 않으며, 모든 조회는 인메모리에서 이루어집니다.
- **단순화된 검증**: 이전 ADR-016에서 강조했던 "데이터 누락으로 인한 윈도우 연산 왜곡(False Positive)" 방어 로직은 파이썬 단의 간단한 `len(deque) < window` 검사 하나로 우아하게 통합되었습니다.
- **메모리 보호**: 가장 무거운 Pandas 오버헤드를 우회했고, MA 데이터는 테이블 스키마를 `STRICT`, `INTEGER` 등으로 압축하여 RAM 사용량을 최소화했습니다.
