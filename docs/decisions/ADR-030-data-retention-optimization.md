# ADR-030: 데이터 보존 주기(GC) 및 콜드스타트 범위 일치 최적화

## Status
Superseded by ADR-031

## Date
2026-08-12

## Context
현재 시스템은 1GB RAM의 오라클 클라우드 환경에서 운영되며, In-Memory DB 아키텍처를 기반으로 단기 돌파(Breakout) 매매 전략을 수행합니다. 
기존 아키텍처는 데이터 수집(Fetch)과 삭제(GC) 정책 간에 심각한 불일치(Mismatch)가 존재했습니다:
- **일봉의 모순**: 콜드스타트 시 약 500영업일 치를 수집하지만, 야간 GC가 300 캘린더 일수 이전의 데이터를 강제 삭제했습니다. 이로 인해 스크리너 핵심 지표인 200일선(MA200, 약 280~300 캘린더 일수 필요)이 데이터 부족으로 붕괴하는 치명적인 결함이 발생했습니다.
- **분봉의 모순**: 콜드스타트 시 약 4.6일 치만 수집하지만, GC는 7일이 경과한 데이터를 보존했습니다. 단기 매매 특성상 200분선(약 2일치) 이상은 필요 없음에도 메모리를 극도로 낭비하는 원인이 되었습니다.

## Decision
수집과 삭제 기준을 1:1로 완벽히 일치시키는 방향으로 정책을 전면 개편합니다.
- **일봉 (500일 정책)**: 콜드스타트 시 최대 500일 치 수집을 유지하고, GC 삭제 기준을 `-300 days`에서 `-500 days`로 연장합니다. 일봉은 용량이 작아 메모리 페널티가 거의 없으며, 이를 통해 전 종목 200일선의 무결성을 완벽하게 보장합니다.
- **분봉 (2일 정책)**: 콜드스타트 시 `max_steps`를 15에서 7(최대 2~3일치 수집)로 대폭 축소하고, GC 삭제 기준을 `-7 days`에서 `-2 days`로 단축시킵니다. 이를 통해 필수 200분선을 유지하면서도 불필요한 분봉 데이터가 차지하던 RAM 용량을 절반 이상 감축(Zero-Overhead)합니다.

## Alternatives Considered

### 종목별 캔들 개수(Row-count) 기준 분할 삭제 (For-loop Chunking)
- **Pros**: 정확히 필요한 캔들 수(예: 200개)만 남겨 가장 이상적인 메모리 확보 가능.
- **Cons**: 2,400개 종목을 루프 돌며 `DELETE`를 수행하면 SQLite에 극심한 파일 락(WinError 32)을 유발하며, 퍼포먼스 저하와 I/O 병목이 초래됩니다.
- **Rejected**: Time-based Bulk GC(`DELETE FROM ... WHERE date < ...`)를 유지하되 임계값만 변경하는 것이 현재의 극단적 최적화 방향에 부합합니다. (참고: ADR-015)

## Consequences
- **MA200 안정성**: 모든 종목에 대해 스크리닝 시 200일선이 누락되는 현상이 근본적으로 차단되었습니다.
- **RAM 다이어트**: 분봉 보존 주기가 7일에서 2일로 감소함에 따라 In-Memory SQLite의 물리적 메모리 상주 용량이 크게 감소하여 전체 앱 안정성이 높아집니다.
- **단기 매매 최적화**: 단기 돌파에 사용되지 않는 오랜 과거 분봉을 과감히 덜어냄으로써 애초의 1GB RAM 돌파 전략 설계 목적에 부합하게 되었습니다.
