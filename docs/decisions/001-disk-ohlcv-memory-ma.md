# ADR-001: OHLCV는 디스크에, MA만 공유 메모리에 유지

## 상태

승인

## 날짜

2026-08-21

## 배경

운영 대상은 1 OCPU·1GB RAM 서버다. 이전 구조는 영속 OHLCV 데이터베이스 전체를 Shared In-Memory SQLite로 복사하면서 별도의 MA 메모리 데이터베이스도 유지했다. 약 202MiB인 영속 DB를 중복 보유해 SQLite 임시 작업, Python, Pandas, OS와 컨테이너가 사용할 메모리 여유가 작았다.

전 종목 연산 비용이 큰 MA 필터는 이미 사전 계산된 `daily_ma`, `minute_ma`를 사용한다. 차트와 수집은 OHLCV 정본이 필요하지만 전체 데이터가 애플리케이션 소유 메모리에 상주할 필요는 없다.

## 결정

- `stock_codes`, `daily_ohlcv`, `minute_ohlcv`는 WAL 기반 `trading.db`를 정본으로 사용한다.
- Shared In-Memory SQLite에는 `daily_ma`, `minute_ma`만 유지한다.
- 스크리너 최대 기간과 교차 판정의 직전 봉을 포함하도록 종목당 일봉 MA 301개, 분봉 MA 391개까지만 유지한다.
- MA 계산 시에는 보존된 OHLCV 원본 전체를 읽어 첫 번째 보관 `ma200`도 정확하게 계산한다.
- 기존 운영 호출명 `sync_memory_to_disk()`는 WAL 체크포인트로 동작한다. `mem_conn`을 명시하는 격리 통합 테스트에서만 메모리 DB를 파일로 backup한다.

## 검토한 대안

### OHLCV 전체를 계속 메모리에 유지

- 임의 조회가 가장 빠르다.
- 가장 큰 데이터를 중복하고 1GB 서버의 안전 여유를 없애므로 제외했다.

### 사전 계산 MA 제거

- 상주 메모리는 줄어든다.
- 전 종목 윈도 계산이 과거 스크리너 지연의 주원인이었으므로 제외했다.

### Go로 서비스 재작성

- 런타임 오버헤드를 줄일 수 있다.
- 모니터링상 CPU 포화가 없고 중복 SQLite 데이터가 Python 런타임보다 큰 메모리 비용이므로 현재는 제외했다.

### 서버 메모리만 증설

- 구현 비용이 가장 작다.
- 하드웨어와 무관하게 불필요한 데이터 중복을 먼저 제거할 수 있으므로 운영 대안으로 남겨둔다.

## 결과

- 애플리케이션 상주 메모리에서 OHLCV 전체 복제본이 제거된다.
- OHLCV 기반 필터와 차트의 블록 볼륨 읽기가 늘 수 있으며 WAL과 OS 페이지 캐시가 가용 RAM 범위에서 이를 흡수한다.
- MA 필터 동작과 200기간 계산 정확도는 유지된다.
- 운영급 서버에서 성능을 다시 측정해야 한다. 특정 OHLCV 필터만 느려질 경우 전체 메모리 DB를 복구하지 않고 작은 전용 hot table을 우선 검토한다.

## 로컬 검증 기준선

2026-08-21에 동일한 약 202MiB `trading.db`와 동일 머신에서 거래량 돌파 필터를 한 번씩 비교했다. 결과 종목 수는 두 방식에서 같았다.

| 필터 | 전체 OHLCV 메모리 복제 | 디스크 정본 | 차이 |
|---|---:|---:|---:|
| 일봉 1개월 | 0.510초 | 0.532초 | +4.3% |
| 분봉 4시간 | 3.332초 | 3.463초 | +3.9% |

단일 실행 결과이므로 이 차이는 측정 노이즈와 OS 페이지 캐시 영향을 포함한다. 운영 배포 후 같은 스크리너 벤치마크와 메모리 RSS를 다시 측정해 최종 판단한다.
