# ADR-004: 라이브 DB 상태 모니터링 API 설계 (Live Status API)

## Status
Accepted

## Date
2026-07-13

## Context
백그라운드 스케줄러가 운영 DB(`trading.db`)에 일봉 및 분봉 데이터를 정상적으로 수집/적재하고 있는지 한눈에 모니터링할 도구가 필요해졌습니다. 기존의 `/admin/test/...` 엔드포인트는 `ContextVar(test_db_var)`를 활용해 테스트용 DB(`test_trading.db`)로 우회하여 파괴적인 검증(삭제/복구)을 수행하지만, 실제 라이브 환경에 적재된 전체 데이터 현황을 직접 눈으로 확인하기 위한 API는 부재했습니다.

## Decision
운영 DB에 직접 쿼리를 날리는 읽기 전용(Read-only) 모니터링 엔드포인트(`/admin/live/...`)를 신설합니다.

1. **라이브 DB 직접 접근**: 이 엔드포인트는 `test_db_var` 컨텍스트 변수를 세팅하지 않고 FastAPI의 기본 `get_db` 의존성을 그대로 사용하여 운영 DB인 `trading.db`를 직접 조회합니다.
2. **순수 조회 쿼리(Read-only) 제한**: DB Lock과 운영 트레이딩 장애를 막기 위해, 데이터 변경 작업(INSERT/UPDATE/DELETE)을 엄격히 배제하고 단순 집계(`SELECT MAX, COUNT 등`) 연산만 수행합니다.
3. **요약 메타데이터 반환**: 1GB RAM 환경에서의 메모리 폭발(OOM)을 방지하기 위해 2,400개 종목의 전체 캔들 데이터를 통째로 반환하지 않고, 데이터 개수, 시작/종료일 등 상태를 점검할 수 있는 요약된 메타 정보만 JSON으로 반환합니다.
4. **소외주 예외 처리**: 거래량이 극도로 적어 달력 상의 날짜가 듬성듬성 수집되는 소외주의 경우, 데이터 최신화가 늦거나 개수가 적어도 시스템 에러가 아니므로 정상적인 상태로 JSON 응답에 포함시킵니다.

## Alternatives Considered
- **테스트 라우터(`/admin/test/...`)에 기능 병합**:
  - Pros: 라우터 Prefix 통합으로 깔끔한 구조 유지.
  - Cons: 기존 테스트 라우터는 호출 시 무조건 `test_trading.db`를 바라보도록 동적 라우팅이 걸려있을 수 있어, 라이브 DB 조회라는 목적과 논리적으로 충돌할 위험이 있음.
  - Rejected: 물리적인 파일은 `admin.py` 하나를 공유하되, 내부적으로 `live_router` 인스턴스를 따로 만들고 접두사(Prefix)를 `/admin/live`로 분리하여 용도를 명확히 구분함.

## Consequences
- 관리자나 향후 연결될 프론트엔드 대시보드에서 라이브 파이프라인의 정상 가동 여부를 파괴적인 테스트 없이 즉각 검증할 수 있게 되었습니다.
- 라이브 운영 DB를 찌르기 때문에, 이후 모니터링 쿼리 확장 시 `LIMIT` 사용이나 효율적인 인덱스(Index)를 활용하여 Full-Scan 오버헤드를 막아야 하는 제약이 따릅니다.
