# ADR-009: 보수적이고 안전한 배포 파이프라인 채택 (Conservative Deployment Pipeline)

## Status
Accepted

## Date
2026-07-23

## Context
본 프로젝트는 Oracle Cloud Free Tier (1 OCPU, 1GB RAM) 인스턴스 위에서 백그라운드 스케줄러와 데이터베이스를 함께 구동합니다.
자동 배포(CI/CD) 과정에서 기존 컨테이너와 새 컨테이너가 일시적으로 공존하는 **무중단 배포(Zero-Downtime Deployment)** 방식을 시도할 경우, 1GB 메모리의 한계로 인해 즉각적인 OOM(Out of Memory)이 발생하여 서버가 완전히 죽어버리는 현상이 발생할 위험이 있습니다.
더불어 `.env` 파일 누락이나 배포 스크립트상의 사소한 오타가 곧바로 DB 마운트 에러나 깡통 컨테이너 배포로 이어지는 문제를 방어해야 할 필요성이 제기되었습니다.

## Decision
무중단 배포를 포기하고, 배포 시 잠시 동안의 다운타임(수십 초)을 감수하더라도 완벽한 안정성을 보장하는 **가장 보수적인(Conservative) 배포 스크립트 작성 원칙**을 채택 및 적용합니다.

1. **Down before Pull & Up**: `docker compose up -d`를 실행하기 전에 반드시 `sudo -E docker compose down`을 실행하여 기존의 모든 컨테이너와 리소스 점유를 해제합니다.
2. **Fail-Fast (`set -e`)**: 모든 배포용 SSH 쉘 스크립트는 최상단에 `set -e`를 포함합니다. 특정 명령어 실행이 실패하면 후속 명령을 중단하고 파이프라인 자체를 에러 상태로 만듭니다.
3. **환경변수 파일 마운트 방어**: `docker-compose.yml`이 파일 단위 마운트를 요구하는 `.env`가 배포 시점에 누락될 경우, Docker가 이를 디렉토리로 오인 생성하여 마운트하는 버그를 막기 위해 배포 직전에 명시적으로 파일 존재 여부(`if [ ! -f .env ]; then exit 1`)를 검사합니다.

## Alternatives Considered

### Blue-Green 배포 (또는 Nginx 무중단 리로딩)
- **Pros**: 사용자가 다운타임을 전혀 인지할 수 없음.
- **Cons**: 2벌의 컨테이너를 동시에 메모리에 올려야 하므로 1GB 환경에서는 100% OOM 발생. 인프라 비용 추가 없이는 불가능함.
- **Rejected**: 리소스 제약 때문에 현실적으로 도입 불가.

### Rolling Update (Docker Swarm / K8s)
- **Pros**: 유연한 복구 및 자동화.
- **Cons**: 단일 노드 서버에 오버헤드가 너무 큼.
- **Rejected**: 프로젝트 규모에 비해 과도한 오버엔지니어링.

## Consequences
- 배포가 진행되는 동안 최대 1~2분가량의 시스템 다운타임이 발생합니다. 하지만 2,400개 종목을 훑는 배치 스케줄러 특성상 하루 4분 레이턴시가 이미 허용(ADR-001)되어 있으므로 배포 중의 짧은 중단은 무시할 수 있는 수준입니다.
- 스크립트 실행이 실패했을 때 에러를 조기에 발견(Fail-Fast)할 수 있게 되어 런타임 장애(컨테이너 꼬임, DB 동기화 오류)를 미연에 방지할 수 있습니다.
- 찌꺼기 이미지 및 로그로 인한 Disk Full 현상을 막아 유지보수 비용이 감소합니다.
