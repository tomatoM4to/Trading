# 📄 [아이디어 원페이지] 하이브리드 In-Memory 이평선 사전 연산 아키텍처

## Problem Statement (해결하고자 하는 문제)
"어떻게 하면 커스텀 이평선의 유연성을 포기하는 대신, 무거운 원본 OHLCV 데이터를 디스크로 밀어내어 70%에 달하는 RAM 점유율을 대폭 낮추고, 스크리너 쿼리를 O(1) 수준의 단순 비교 연산으로 만들어 지연 시간(Latency)을 획기적으로 줄일 수 있을까?"

## Recommended Direction (권장 방향)
**물리적 이평선 테이블 분리 및 선별적 In-Memory 로딩**
데이터를 '저장용'과 '연산용'으로 완벽히 분리합니다.

1. **디스크 영구 저장 (`trading.db`)**: 
   - 원본 캔들 테이블(`daily_ohlcv`, `minute_ohlcv`)
   - 사전 연산된 이평선 테이블(`daily_ma`, `minute_ma`) 
   - ➔ 모든 데이터는 디스크에 영구 보존됩니다.
2. **선별적 In-Memory 로딩 (Bootstrapping)**: 
   - 서버 기동 시, 기존처럼 전체 DB를 인메모리로 복제하지 않습니다. 
   - 무거운 OHLCV 원본은 디스크에 그대로 내버려두고, **오직 스크리너 연산에 필요한 `daily_ma`와 `minute_ma` 테이블만 인메모리 DB로 로드**합니다.
3. **스케줄러와 주기적 동기화 (Sync)**: 
   - 장중(09:00~15:30)에는 분봉 스케줄러가 파이썬으로 이평선을 계산하여 인메모리 `minute_ma` 테이블을 실시간으로 업데이트합니다.
   - 기존의 스케줄러 룰(08:30, 16:00, 23:00)에 따라, 메모리에서 업데이트된 이평선 데이터들을 디스크 DB로 주기적으로 백업(Sync)하여 휘발을 방지합니다.

## Key Assumptions to Validate (반드시 검증해야 할 숨은 가설)
- [ ] **가설 1**: 사용자는 커스텀 이평선 대신 시스템이 제공하는 고정 이평선(5, 10, 20, 60, 120, 200)만으로도 매매 전략 수립에 지장이 없다.
- [ ] **가설 2**: 2,400개 종목에 대한 실시간 이평선 연산을 무거운 Pandas 대신 순수 파이썬(Pure Python) 내장 리스트 연산으로 처리하면, 1GB RAM 환경에서도 메모리 오버헤드 없이 압도적으로 빠르게 계산될 것이다.
- [ ] **가설 3**: 차트를 그리기 위한 단일 종목 디스크 읽기(Disk I/O) 속도는 클라이언트 UX에 영향을 주지 않을 만큼 빠르다.

## MVP Scope (최소 기능 구현 범위)
- **이평선 스펙 확정**: 일봉/분봉 공통으로 알고리즘 트레이딩에 최적화된 6개 칼럼(`ma5`, `ma10`, `ma20`, `ma60`, `ma120`, `ma200`) 고정.
- **스키마 재설계**: `daily_ma`, `minute_ma` 독립 테이블 설계.
- **부트스트랩 분리**: `init_db` 로직에서 `ohlcv`는 디스크 전용으로 남기고, `ma` 테이블만 `file::memory`로 덤프(Dump) 뜨는 기능 구현.
- **스크리너 쿼리 개편**: `active_tickers` 내부의 Window 함수 생성 로직 제거, 인메모리 `ma` 테이블 직접 조회로 롤백.
- **스케줄러 개편**: 데이터 적재 전 외부 라이브러리(Pandas 등) 없이 순수 파이썬(Pure Python) 내장 리스트 연산(`sum`)으로 이평선을 초경량 연산한 뒤, 이평선 테이블에 동시 삽입 및 주기적 디스크 Sync 구현.

## Not Doing (우리가 하지 않을 것과 그 이유)
- **커스텀 이평선 일수(Period) 지원**: 무거운 런타임 윈도우 함수를 제거하기 위해 과감히 포기합니다.
- **부팅 시 실시간 이평선 재계산**: CPU 스파이크를 막기 위해, 디스크에 이미 계산되어 저장된 이평선 테이블을 그대로 메모리로 떠올리기만 합니다.
- **원본 OHLCV의 인메모리 상주**: OOM 방지와 RAM 70% 점유율 해소를 위해 포기합니다. (디스크 I/O로 우회)
