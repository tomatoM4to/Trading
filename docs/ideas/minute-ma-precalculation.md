# 분봉 이평선 수집 단계 사전 연산 (Minute MA Precalculation)

## Problem Statement
어떻게 하면 1 OCPU / 1GB RAM 서버 환경에서 60초 이상의 타임아웃을 유발하는 무거운 분봉 윈도우 연산(Window Function) 부하를 완벽히 제거하여 스크리너 응답 속도를 1초 미만으로 단축시킬 수 있을까?

## Recommended Direction
사용자가 스크리너를 호출할 때 DB 엔진단에서 실시간 윈도우 함수를 돌리는 기존 방식을 폐기합니다. 
대신, 장중(09:00~15:30) 분봉 데이터를 수집하는 `minute_ohlcv` 스케줄러가 KIS API에서 데이터를 받아올 때, 현재 100% 인메모리로 동작하고 있는 SQLite(`trading.db`)를 적극 활용하여 즉시 MA(5, 10, 20, 60)를 계산하고 테이블에 직접 INSERT 합니다.
사용자 요청 시 무거운 윈도우 함수 없이 단순 `WHERE ma5 > ma20` 형태의 상수 비교 쿼리만 수행하므로 O(1)에 가까운 초고속 응답을 보장합니다.

## Key Assumptions to Validate
- [ ] **메모리(RAM) 증가량 한계**: 분봉 테이블(`minute_ohlcv`)에 최대 4개의 추가 컬럼(ma5, ma10, ma20, ma60)을 추가하고 7일 보관 주기(GC)를 유지했을 때 1GB RAM을 초과하지 않는가? (계산상 매우 안전함)
- [ ] **수집 워커의 연산 병목 여부**: 인메모리 SQLite에서 최근 60개 캔들을 `SELECT` 하여 Pandas로 평균을 내는 연산이 0.1초(Global Rate Limit 딜레이) 내에 충분히 완료되어 수집 큐 전체를 지연시키지 않는가?

## MVP Scope
- 분봉 수집 스케줄러 내부에 이평선 사전 계산 로직 추가 (인메모리 DB에서 최근 60개 캔들 Select 후 연산).
- `minute_ohlcv` 테이블 스키마에 `ma5, ma10, ma20, ma60` 컬럼 추가 (STRICT 유지).
- 스크리너 서비스(`screener_service.py`)의 분봉 연산 쿼리에서 윈도우 함수(`AVG() OVER...`) 구문을 걷어내고 단순 컬럼 비교 쿼리로 전면 리팩토링.
- (향후 확장) 디스크 용량이 충분하므로 일봉(`daily_ohlcv`) 데이터 역시 장 마감 후 정규 스케줄러를 통해 MA를 사전 계산하여 컬럼으로 적재.

## Not Doing (and Why)
- **자체 커스텀 메모리 캐시(Python Dict 등) 구축 금지**: 이미 `trading.db`가 100% 인메모리(Shared Cache)로 완벽히 동작 중이므로, 파이썬 레벨에서 별도 큐나 배열을 유지하면 상태 동기화 버그만 유발함. 인메모리 DB를 캐시처럼 활용하는 KISS 원칙 준수.
- **모든 이평선(120선, 200선 등) 지원 금지**: 단기 매매(분봉)에서 3~4일 전 데이터 기반의 장기 이평선은 유효성이 떨어지므로, DB 공간과 메모리 낭비를 막기 위해 최대 60선까지만 계산하고 제공함.
- **캔들 갭(Gap)을 메우기 위한 결측치 보간 금지**: 데이터가 부족해 MA60이 계산되지 않는 구간(예: 갓 상장한 종목, 거래정지 직후)은 단순히 `NULL`로 삽입함. 사용자가 스크리너로 `ma5 > ma60`을 조회할 때 SQLite가 NULL을 자동으로 필터링하므로 비즈니스 로직을 극도로 단순화함.

## Open Questions
