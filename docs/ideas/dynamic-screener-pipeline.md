# 📝 아이디어 명세: Set-Theory 기반 다이내믹 스크리너 파이프라인

## 🎯 Problem Statement (문제 정의)
어떻게 하면 클라이언트가 동적인 파라미터를 던져 다수의 기술적 지표(이평선, 수렴, 이격도 등)와 수급 지표(외국인/기관 매수량)를 독립적으로 평가하고, 이들의 교집합/합집합(AND/OR)을 1GB RAM 환경에서 메모리 폭발이나 API Rate Limit(초당 20건) 초과 없이 실시간으로 계산할 수 있을까?

## 🧭 Recommended Direction (권장 방향)
**Set(집합) 연산과 지연 평가(Late Evaluation)를 결합한 Pipeline Architecture**

모든 지표 계산을 파이썬 메모리가 아닌, 독립된 서비스 함수(DB 쿼리 또는 외부 API)가 처리하도록 위임하며, 각 함수는 **'종목 코드들의 집합(Set[str])'**만을 반환합니다.

특히 외부 API(수급 데이터)를 호출해야 하는 무거운 필터는 파이프라인의 **가장 마지막**에 배치하여 호출 횟수를 극적으로 줄입니다(지연 평가).

1. **Local DB Filter 1**: `filter_convergence(margin=0.05)` 실행 ➡️ 로컬 SQLite에서 즉시 처리 후 `{"005930", "000660", ...}` (30개 반환)
2. **Local DB Filter 2**: `filter_alignment(lines=[60, 120], duration=3)` 실행 ➡️ 로컬 SQLite에서 즉시 처리 후 `{"005930", "035420", ...}` (15개 반환)
3. **Set Intersection (파이썬)**: 위 두 결과의 교집합 `&` 연산 ➡️ `{"005930", "035420"}` (단 2개로 압축됨)
4. **External API Filter (수급)**: `filter_foreign_buy(min_vol=10000)` 실행 ➡️ 2,400개 전 종목을 KIS API로 찌르는 것이 아니라, 위에서 통과된 **단 2개의 종목만 API로 조회**. (Rate Limit 완벽 회피 및 0.1초 내 응답 완료)

파이썬은 단지 이 얇은 Set(문자열 배열)들을 받아 `&` (AND), `|` (OR) 연산만 수행하므로 메모리를 전혀 쓰지 않으면서도 무한한 제어 논리 확장이 가능합니다.

## ⚠️ Key Assumptions to Validate (검증해야 할 핵심 가정)
- [ ] **DB 연산 부하**: 실시간으로 2,400개 종목에 대한 이격도 및 이평선 쿼리를 SQLite가 인덱스를 통해 수 초 내에 감당할 수 있는가?
- [ ] **KIS API 수급 데이터**: `investor_trade_by_stock_daily` (종목별 투자자매매동향) API가 실시간 장중 수급을 충분한 신뢰도로 제공하는가? (장 마감 후 집계 데이터인지, 장중 추정치인지 확인 필요)
- [ ] **API 인터페이스 합의**: 의뢰자가 JSON 형태로 트리 구조의 쿼리(예: `{"op": "AND", "filters": [...]}`)를 구성하는 것에 동의하는가?

## 🚀 MVP Scope (최소 기능 구현 범위)
- **In Scope**:
  - `AND`, `OR` 연산을 파싱하여 각 서비스 함수로 분배하는 중앙 파이프라인 API(Screener Engine).
  - 4가지 로컬 DB 코어 모듈: 이평선 수렴(오차율 파라미터), 이평선 정배열, 이평선 크로스, 이격도.
  - 1가지 외부 API 모듈: 종목별 투자자 매매동향(외국인/기관 순매수) KIS OpenAPI 연동 모듈. (단, 파이프라인의 후순위 필터로 강제 동작하도록 엔진 단에서 순서 제어)
- **Out of Scope**:
  - 매물대(Volume Profile) 및 추세선. (연산 로직이 고도화되어야 하므로 파이프라인 엔진 뼈대가 안정화된 후 추가).
  - 재무제표 (수익성, 사업 등 후순위 지표).

## 🛑 Not Doing (and Why) - 명시적 포기
- **Pandas DataFrame을 활용한 파이프라인 전달**: 1GB RAM 메모리 한계로 인해 데이터 프레임 교집합은 절대 구축하지 않습니다. 오직 Ticker(종목코드) 집합만 취급합니다.
- **수급 데이터 로직의 전방 배치**: 2,400개 전 종목을 외부 API로 긁어오는 무식한 배치는 하지 않습니다. 수급 지표 필터링은 항상 교집합이 어느 정도 이루어진 최종 후보군(수십 개 이하)에 대해서만 작동하도록 막아둡니다.
- **정적 캐싱(Static Caching)**: 파라미터가 동적이므로(예: 3% 수렴 vs 5% 수렴) 일괄 캐싱 구조는 배제합니다.
